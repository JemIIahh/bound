# MPP spike: mppx 0.13.1 with a Tempo access key on Moderato (2026-10-07)

Probe: `apps/server/scripts/mpp-spike.ts` (`TEMPO_NETWORK=testnet tsx scripts/mpp-spike.ts`). It authorizes a throwaway agent
key on the demo root (allowlist: the Acme demo payee only, 1 pathUSD/day), serves a throwaway `mppx/express` API on port 0, and
pays it honest and hijacked (`?hijack=1` names `LAB_LOOKALIKE_ADDRESS`) in pull and push mode. Ran 4 times, same result each time.
**Prerequisite:** mppx 0.13.1 needs viem ≥ 2.57.1 (on 2.57.0 it crashes at import: `The requested module 'viem/tokens' does not
provide an export named 'ousd'`). `apps/server` now asks for `viem ^2.57.3`; the lockfile is deduped to one viem 2.57.3.

## Signer

`Account.fromSecp256k1(agentKey, { access: rootAddress })` from `viem/tempo` (`agentAccount()` in `@bound/core`), passed as-is:
`tempo.charge({ account: agent, getClient, expectedChainId: 42431, allowedChainIds: [42431] })` from `mppx/client`,
`Mppx.create({ methods: [...], polyfill: false })`. No wallet provider needed. The charge is one `transferWithMemo` call (mppx
always sets an attribution memo), so the key's existing Bound scope (pathUSD, `transferWithMemo` only, recipient allowlist)
covers it. The root pays gas in pathUSD (no fee payer). **Always pass `getClient` (Moderato) and `expectedChainId`:** the
client's default chain is Tempo mainnet (`rpc.tempo.xyz`) when a challenge omits `chainId`.

## Mode

**Both work.** Use **`pull`** (mppx's default for local accounts, so `mode` can be omitted): the client signs, the API
broadcasts and waits for the receipt. `push` (agent broadcasts with `sendTransactionSync`, sends the hash) also returned 200.
Both sign with `nonceKey: 'expiring'` and a `validBefore` of at most 25 s.

## Server snippet

```ts
import { Mppx, tempo } from 'mppx/express'
const mppx = Mppx.create({
  methods: [tempo.charge({ testnet: true, currency: PATHUSD, getClient })], // getClient → Moderato client only
  secretKey: process.env.MPP_SECRET_KEY, // ≥ 32 bytes or Mppx.create throws; HMAC-binds challenges
  realm: 'bound-demo-api',
})
app.get('/paid', (req, res, next) =>
  mppx.charge({ amount: '0.01', currency: PATHUSD, recipient: req.query.hijack ? LOOKALIKE : ACME, description: '…' })(req, res, next),
  (_req, res) => { res.json({ data: '…' }) })
```
The 200 carries `Payment-Receipt` (`Receipt.deserialize` from `mppx`): `{"method":"tempo","reference":"0x<payment tx hash>","status":"success",…}`.

## Rejected payment

Hijacked (recipient not on the allowlist), both modes: `mppx.fetch` **throws** the raw viem error (mppx does not wrap it):
`TransactionExecutionError`, `shortMessage` = `Execution reverted with reason: Account keychain error: CallNotAllowed(CallNotAllowed).`
Cause chain `TransactionExecutionError > ExecutionRevertedError > RpcRequestError` (push nests it twice);
`decodeTempoError(e).code === 'CallNotAllowed'`. It fails in the node's simulation while the client prepares the transaction:
**nothing is broadcast, there is no tx hash**, the API never receives a credential (0 `Authorization: Payment` retries) and the
lookalike's balance stays 0. No HTTP status: the 402 is consumed inside `fetch`.

## Fallback needed

**No.** The access key signs MPP payments in both modes. One consequence for Tasks 5–6: with the guard off, the hijacked mppx
payment is refused by Tempo pre-broadcast, so it has no explorer link. If the demo wants a mined, reverted tx to link to, use
the existing lab path (`forceSendWithKey`, testnet only) with the challenge's recipient; otherwise show `CallNotAllowed` with no link.

## Challenge shape

`payment.challenge` from `rawFetch` + `preparePayment(res, { request: {} })` (no signing):
```json
{"id":"<hmac>","realm":"bound-mpp-spike","method":"tempo","intent":"charge","description":"spike data",
 "expires":"2026-10-07T15:03:31.808Z","opaque":"<base64url {\"_mppx_scope\":\"GET /paid\"}>",
 "request":{"amount":"10000","currency":"0x20c0000000000000000000000000000000000000",
            "methodDetails":{"chainId":42431},"recipient":"0xc1a53DA961B7A3A62db84Ae889f57fa818d3C426"}}
```

- `request.amount` is a **base-units integer string** (`"10000"` = 0.01 pathUSD) and is the **total**. The server is given
  `'0.01'`; it converts. `decimals` is **not** in the challenge (dropped by the schema), so assume 6 for Tempo TIP-20.
- The wire `request` (base64url JSON in `WWW-Authenticate: Payment …, request="…"`) is identical to the parsed one.
- `recipient` is a string address in whatever case the server used (checksummed here): normalize before comparing.
- `methodDetails.chainId` is a number (42431). With splits (`/split` route):
  `"methodDetails":{"chainId":42431,"splits":[{"amount":"2000","recipient":"0xC1A5d69D86Dea5CA36F7aE391b6610CfFB96C426"}]}`.
  Split amounts are base units (optional `memo`); the primary recipient receives `amount − Σ splits` (8000 here).
- `description` and `expires` (about 5 min) sit on the challenge, not on `request`. mppx's own client option
  `expectedRecipients` (a static list, not a Bound check) throws `Unexpected primary recipient: 0x…` before signing.
